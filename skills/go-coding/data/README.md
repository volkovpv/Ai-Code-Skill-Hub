# Data contract — go-coding

- **Purpose**: reproducible Go inputs for the convention checker.
  `fixtures/` feeds the automated tests of this skill and ships only in
  `full` installs — a `runtime` install strips it (see the Layout convention
  below), so shipped prose must not link into it; `examples/` ships in every
  install mode and shows a minimal input/expected-output pair that
  calibrates the checker's format.
- **Source / generation**: hand-written synthetic Go; no real project code.
  `fixtures/clean_sample.go` is additionally verified outside the library
  (it compiles on Go 1.27.1 and passes `go vet` and the reference
  golangci-lint configuration with zero issues); the other fixtures are
  checker inputs and need not compile. Regenerate by editing the files
  directly. After editing the example input, refresh
  `examples/checked_input.expected` by running the checker on
  `examples/checked_input.go` via stdin.
- **License**: MIT (same as the skill; see ORIGIN.yaml).
- **Format**: `.go` source files; the expected checker output is a
  plain-text `.expected` file (one finding per line,
  `label:line: CODE message`).
- **Allowed use**: input for `scripts/check_go_conventions.py` in tests and
  demos. The data never overrides the agent's own judgement about real code.
- **PII / secrets**: none — every identifier, path and value is invented; the
  library's secret scan runs over this directory on every validation.
- **Update procedure**: edit → `skillctl validate go-coding` →
  `skillctl test go-coding` → bump `version` in skills.yaml.
- **Size limits**: each file stays far below the default
  `content_policy.max_tracked_file_bytes` (256 KiB); anything larger must be
  generated by a script instead of committed.
- **Go tooling in a consumer project**: installs land under a directory whose
  name starts with a dot (`.claude/`, `.agents/`), which `go build ./...`,
  `go vet ./...` and golangci-lint skip, so these `.go` files never join a
  consumer's build.

Layout convention:

- `fixtures/` — test-only inputs; **not** installed in runtime mode. Contents:
  - `clean_sample.go` — idiomatic Go 1.27 (typed enum, sealed interface,
    wrapped errors, bounded fan-out, SQL placeholders, HTTP with timeouts,
    `os/exec` without a shell, `os.Root`, `crypto/rand`); the checker finds
    nothing;
  - `violations.go` — exactly one violation per checker rule, including the
    security rules (`GO-SQL-FMT`, `GO-SHELL`, `GO-TLS-INSECURE`,
    `GO-HTTP-TIMEOUT`);
  - `masked_literals.go` — every rule quoted inside comments, interpreted
    strings, raw strings and runes; the checker must stay silent (pins the
    lexical masking);
  - `app_config.go` — a config-layer file (environment access is legitimate
    here); evidence for the path-context limitation: the same content piped
    through stdin (no path) is flagged;
  - `justified_nolint.go` — the sanctioned single-linter/-check/-rule
    suppression forms with written reasons; `GO-SUPPRESS` must not flag them;
  - `cmd_main.go` — a `package main` entry point, where `os.Exit` and the
    root context are legitimate (its output still goes through an injected
    writer); verified with the same toolchain and configuration as
    `clean_sample.go`;
  - `generated_sample.go` — a file with the standard `// Code generated ...
    DO NOT EDIT.` header, skipped entirely.
- `examples/` — minimal input/output pairs shipped to consumers:
  - `checked_input.go` + `checked_input.expected` — a calibrated run of the
    checker over stdin (label `<stdin>`). Note: the `return
    errors.New("charge failed")` line deliberately produces no finding — it
    drops the cause of the failure, a defect a lexical checker cannot see and
    one the error rules in the references cover.

## Context (input)

Three independent occurrences across a consumer (`news-intel-docs`) agent-plane build
(RM-TASK-017: AMQP client + idempotent consumer/manual-ack/DLQ + LangGraph checkpoint store).
In every one, a unit-test fake for a third-party seam — the RabbitMQ broker (via `aio-pika`),
the `aiormq` SASL-PLAIN encoder, and the `psycopg` `dict_row` row factory — stayed green while
encoding a belief about that system's runtime behaviour that was simply wrong, and only a live
probe against the real system (never a re-reading of the project's own norm or the vendor's
documentation) ever caught it. Full evidence trail in the consumer's
`harness/review/skill-triage-2026-07-26.md` §2 (verdict C3, both threshold limbs independently
re-verified by the Reviewer's own execution).

The skill loaded and was followed throughout: every fake was placed at the seam
`references/testing.md` prescribes ("fake protocols and seams the code exposes, never someone
else's internals"). The gap is not a coding mistake and not a project-local norm question — it
is the absence of guidance on how the reference behaviour a fake encodes for an **external**
system gets established in the first place, on which `references/testing.md` is silent.

## Expected behavior

**A fake's own return values, when the property under test belongs to an external system, are
established by observing that system once, never by reading.** When the subject is a broker, an
authentication encoder, a driver's row factory, or any other third-party system the project does
not own, no fake, and no re-reading of a project norm, an RFC, or vendor documentation, can
establish what that system actually does — only a live observation against the real system can.
Write the fake only after a probe against the real system has pinned the behaviour, then reuse
that pinned observation as a fixture rather than re-deriving it from prose on every subsequent
change. Operational trigger: treat a second rejection of the same reading on the same
external-system property as the signal to switch evidence class from reading to a live
observation, not as cause to produce a third reading.

## Actual behavior

First-upstream-failure summary, one per occurrence, against three different third-party systems:

1. **`aio-pika`/RabbitMQ** — the event name was taken from a routing key. The broker rewrites
   the delivery key at every dead-letter hop while carrying `type` through unchanged. Two
   consecutive fix rounds each picked a different key by re-reading the project's own routing-key
   convention doc; a unit-test fake for the publisher port encoded whichever wrong belief was
   current and stayed green throughout — only a live two-hop TTL/DLX probe against the real
   broker settled it.
2. **`aiormq`** — a non-blank check at the settings layer looked sufficient by reading the code
   path one layer up. The SASL-PLAIN encoder substitutes a default identity for a username that
   is absent **or empty**, one layer below the wrapper under test; no fake at the wrapper's own
   seam could see this, because the fake's job was to stand in for the very layer that does the
   substitution. Only a live probe against the real broker exposed it.
3. **`psycopg`** — two un-aliased boolean columns collapse into a single key under `dict_row`, so
   `fetchone()` returned a one-item mapping. The unit-test fake for the schema-check cursor was
   written as a plain tuple — the ordinary DB-API expectation, and exactly wrong for a connection
   opened with `row_factory=dict_row` (the library's own choice). Only a live query against the
   real database produced the failure.

## Minimal reproduction

Two of the three occurrences reduce to a deterministic, project-independent, self-contained
snippet; the third (a live two-hop broker DLX cycle) is not reducible to one, which is itself
part of what this observation is about — a topology-dependent broker behaviour of this kind
cannot be established by reading the AMQP 0-9-1 spec prose either, only by observing the pinned
broker version.

- `yarl.URL.build(scheme="amqp", host="h", port=1, user="", password="p").user` — always `None`
  on an empty string, regardless of any project-specific code; whatever client library reads that
  URL is free to substitute its own default identity for the absent user. Re-executed by the
  consumer Reviewer, confirmed.
- `psycopg.rows.dict_row` with `SELECT true AS a, false AS b` versus the unaliased
  `SELECT true, false` — the second form's `cur.fetchone()` returns a one-key mapping
  deterministically, on any PostgreSQL instance. Re-executed by the consumer Reviewer against a
  live PostgreSQL 18.4 instance: `{'a': True, 'b': False}` vs `{'?column?': False}`, confirmed.

## Universality check

Independent of any local norm: the subject in all three cases is the behaviour of a third-party
system this project does not control and did not write — a broker, an authentication encoder, a
database driver's row factory. SFL-INV-08 is met on both limbs: 3 independent occurrences in
different files against three different libraries in one consumer task, and two of the three have
a deterministic, project-independent minimal reproduction, both independently re-executed by the
consumer's own Reviewer (not merely taken on the observation's word).

## Suggested fix (delta-sized)

Add one guidance block to `references/testing.md`, adjacent to the existing fake-the-seam rules:
the reference behaviour a fake encodes for an external system is established once, by observing
the real system, and pinned as a fixture — never assumed from project-normative prose, vendor
documentation, or a second reading of either after a first reading was already rejected, with the
second-rejection-switches-evidence-class operational trigger. Ship both deterministic minimal
reproductions above as the rule's illustrative snippets so it is checkable, not merely
aspirational.

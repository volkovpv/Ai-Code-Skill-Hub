## Context (input)

A field report from a consuming project's build of a settings/configuration module.
A fail-closed settings-construction path wraps a third-party schema-validation
library's own exception in a typed, name-only error (`raise NameOnlySettingsError(...)
from err`, per this skill's "wrap at most once, preserve the cause" rule) and the
top-level handler logs the full chain including `__cause__` (per this skill's "report
with the stack" rule). The library's own validation exception embeds the rejected input
value in its own `str`/`repr` for debuggability, and for a model-level (not per-field)
validator the "offending value" it attaches is the whole input mapping, not one field.
Both individual rules were followed to the letter; the chained cause's own text still
carried the un-redacted input.

## Expected behavior

The skill's error-handling guidance should name this composition: "wrap once, preserve
the cause" plus "report with the stack, `__cause__` included" is exactly right for an
ordinary internal exception, but becomes a disclosure channel the moment the wrapped
cause is a third-party validation/parsing exception whose own string form echoes
untrusted or sensitive input. The skill's logging guidance already names the adjacent
case — never log a secret or a whole request body — but does not connect that rule to
"report with the stack, `__cause__` included," so a careful author can satisfy both
rules individually and still leak the value through the chained cause's own `repr`.

## Actual behavior

Neither the chaining rule nor the logging rule warns that "the full chain" can itself
be the leak channel when a wrapped library exception is echo-y by construction.
Applying the guidance as written — catch narrow, wrap once with `from err`, log the
full chain at the boundary — does not surface this.

## Minimal reproduction

Project-independent:
1. Define a settings/config model with a library-provided validator (any
   schema-validation library that stores the rejected value on its exception for
   debuggability) and a model-level (not per-field) validation rule, so the
   "offending value" the library attaches to its exception is the whole input mapping,
   not one field.
2. At the boundary, catch that library exception and re-raise a project-typed error
   whose own message is deliberately name-only / value-free — following "wrap once,
   preserve the cause" to the letter.
3. At the top-level handler, log the full chain including `__cause__` — following
   "report with the stack" to the letter.
4. Trigger the validation failure with an input containing a secret-shaped value.
   Observe a value-derived fragment of the secret in the emitted log — the visible
   extent is library-dependent (a library's own `repr`-length limit may truncate it),
   but the rejected value reaching the emitted chain at all is deterministic — despite
   both individual rules having been followed correctly.

## Universality check

Nothing above is specific to one validation library or one project's settings surface:
any service that (a) validates configuration/input with a third-party library that
attaches the rejected value to its own exception, and (b) follows a generic "preserve
and log the full chain" error-handling discipline, reproduces the same leak channel.
The skill already states both individual rules as universal; the interaction is the gap.

## Suggested fix

A clause near "report with the stack" naming the composition explicitly: when the
wrapped cause is a third-party validation/parsing exception, either (a) do not log
`__cause__` at that boundary and instead log only the wrapper's own typed, scrubbed
message, or (b) scrub the cause's own string form before it reaches any sink governed
by "report with the stack."

# Two grounds absent from the DRY/security guidance: detection boundary and the union-of-callers rule

## Context (input)

A field report from a consuming project's build (Reviewer-confirmed C3;
`SFL-INV-08` met on both limbs). The project's own tree measured a large
class of duplicated implementations across independently maintained
modules: one repository-style adapter's core method was byte-identical
across more than a dozen call sites introduced in over ten separate tasks,
and a defensive parser standing over untrusted model output existed in five
independently maintained copies. The harm this enabled was independently
measured too: one incorrect nullable-value coercion line was copied to
several sites; after a review named the defect at three of them, the family
had grown further while the fix reached only two, leaving the rest
unguarded — in one file the unprotected line stood two lines above a
correctly protected sibling.

The skill's existing "DRY at the type level" section addresses only type
declarations and signatures, never implementations, so the first framing of
this gap ("no sentence addresses implementation-level duplication at all")
was checked against the skill's own `lint-clean.md` and found **false as
stated**: `lint-clean.md` already states "no duplicated or identical
branches, conditions, or functions — factor the shared body out," with no
tool name and no scope. Had that been the whole gap, this would be a
project-local (C2) tightening of an already-correct rule, not a C3 transfer.
Two things remain genuinely absent from the skill, independent of any
project's own rules, and are the actual basis for this record.

## Expected behavior

(a) A rule stated in prose ought to say whether the stack's own tooling
backs it, so a green run is not mistaken for confirmation. (b) A skill
covering security and untrusted-input handling ought to state that
collapsing a defensive/parsing routine over untrusted input to a shared
implementation means giving it the union of every caller's cases, not
leaving each independently-maintained copy to cover only what its own
author tested against.

## Actual behavior

(a) Nothing in the skill states that this stack's own blocking linter
carries no rule of this class at any configuration, nor that the detector
which does exist for it (a line-based duplicate-code check) is blind to
identifier renaming. The bullet lives inside a lint-conformance reference,
where a green run of the stack's actual blocking gate reads as the
obligation being met — for this one bullet a green run means nothing,
because the blocking linter cannot check it, and the skill does not say so.

Re-executed live against `pylint` 4.0.6's `duplicate-code` (`R0801`) on a
three-package scratch tree outside this library: a cross-module copy with
five identifiers renamed scores `10.00/10`, zero findings; the verbatim
(unrenamed) cross-module control fires as expected. The stack's actually
blocking linter (`ruff`) carries no rule of this class at any configuration
in its full rule set.

(b) Neither the security guidance, the type-design boundary-parsing
guidance, nor the runtime-correctness guidance states that a defensive
routine over untrusted input must be collapsed to the union of every
caller's cases rather than duplicated per caller. The measured instance: a
parser over untrusted model output, independently duplicated across several
call sites introduced in separate tasks, each covered by tests tied to only
its own caller's scenario.

## Minimal reproduction

Deterministic, project-independent (any Python project following this
skill's stack):

1. `pkg_a/adapter.py`: `def to_int_or_none(raw: object) -> int | None: ...`
   (a small defensive coercion).
2. `pkg_b/adapter.py`, a different module: the identical body under a
   renamed function and parameter (five identifiers renamed).
3. Run `pylint` with `duplicate-code` (`R0801`) enabled over the tree.
   Result: zero findings, `10.00/10` — renaming five identifiers is
   sufficient to make a byte-identical implementation invisible to this
   detector. The project's blocking linter (`ruff`, its full pinned rule
   set) has no rule of this class at all, so the class is invisible to the
   blocking gate unconditionally and to the advisory gate the moment a
   variable is renamed.
4. Control: copy `pkg_a/adapter.py` verbatim (no rename) to `pkg_c/adapter.py`.
   `duplicate-code` now reports the pair — confirming the detector was
   working and that step 3's silence is the rename tolerance specifically.
5. Separately: two independently-maintained copies of a defensive parser
   over untrusted input, each tested only against its own caller's
   historical malformed inputs. A case only one caller's real input
   produces is silently unguarded in the other copy, and a fix applied to
   one copy in response to its own caller's bug report does not propagate
   to the sibling.

## Universality check

Nothing above depends on this project's rules, module layout, or specific
adapters — only on the documented behavior of `pylint`'s `duplicate-code`
check under renaming, on the absence of any such rule in `ruff`'s full rule
set, and on the general property that per-caller duplication of a defensive
routine covers only the union tested, not the union needed. `SFL-INV-08`'s
first limb is met by several independently occurring, differently-typed
clusters on the reporting project's own tree, introduced across unrelated
tasks; its second limb is met by the reproduction above.

## Suggested fix

(a) State next to the duplication bullet in `lint-clean.md` that this
stack's blocking linter carries no rule of this class and that the advisory
detector is blind to renaming — a green run does not confirm the rule. (b)
Add a rule to `security.md` (or the nearest untrusted-input section):
collapsing a defensive/parsing routine over untrusted input into one shared
implementation means the union of every caller's cases, never a pick of
one.

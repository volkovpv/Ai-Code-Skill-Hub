## Context (input)

Nine independent occurrences across a consumer's (`news-intel-docs`) agent-plane observability-skeleton
build, spanning thirteen rounds, all found by either a live probe or a mutation battery, **never by the
test suite that was supposed to guard the property**. Full evidence trail in the consumer's
`harness/review/skill-triage-2026-07-25.md` §2–§7 (final verdict §7, `approved`, `occurrences: 9`);
consumer observation `harness/observations/OBS-20260726-001.md`.

The skill loaded and was followed throughout: every round shipped a red-before-green regression test
alongside its fix, and reported a healthy mutation score wherever mutation testing was run. The gap is
not a coding mistake — it is the *absence of guidance* on how a test's case set, its subject, and the
dimensions it must vary are chosen, on which `references/testing.md` §Hygiene is silent. Its only nearby
rule ("do not tune a test to the gate: never hardcode an expected value so it passes") does not reach any
of the nine occurrences — nothing was hardcoded to pass, and every case was genuinely red before its fix.

## Expected behavior

Three rules, one family — *a test's cases, its subject, and its dimensions are all chosen from the
specification, never from the artifact under test*:

1. **Provenance of the case set.** A test's case set is derived from the *specification's* class, never
   copied from — or parametrized over — the artifact under test. A healthy mutation score is not
   evidence of specification coverage: when the case set mutates together with the implementation, the
   mutant is killed and the unmet specification stays invisible.
2. **Subject of the test under layered protection.** When a property is protected by more than one
   layer, a test that reaches it through the **outer** layer proves nothing about the inner one; a
   defence-in-depth claim is unverified until each layer is exercised on a path where it is the
   **only** protection. Equivalently: every layer needs a test that goes red when that layer alone is
   deleted.
3. **Totality of the case set across the dimensions the control discriminates on.** A parametrized set
   that varies **one** dimension of the input says nothing about the others, and its size is not
   evidence: eleven cases over eleven names cover one dimension eleven times. Where the implementation
   carries a dedicated mechanism for another dimension (a raised-vs-lying dunder, a raw-vs-normalized
   key form, an `Exception`-vs-`BaseException` boundary, a sole-protection-vs-one-of-two-guards
   channel), that mechanism is by construction untested until the case set varies that dimension too.
   Operational form: for each guard, name the dimensions of the input it discriminates on, and require
   at least one case per dimension — treat a surviving mutation as evidence of a missing **dimension**,
   not merely of a missing case.

## Minimal reproduction

Three deterministic, project-independent, self-contained reproductions — one per rule:

**Rule 1 (provenance):** an implementation exposing `ALLOWED = {a, b, c}` for a rule the specification
states as an open class; a test parametrized over that same `{a, b, c}`; a mutation of the
implementation set (`"totalTokens"` → `"totalTokensXX"`) turns the test red (healthy mutation score);
one specification-class member `d` (e.g. `totalTokenCount`) is silently unhandled and no test notices.
Stricter variant: if the test *imports* the enumeration rather than copying it literally, the mutation
does not even fail (`3 passed` both before and after) — mutation testing is blind to the pattern.

**Rule 2 (layered subject):** a value guarded both by an upstream filter and by an unconditional
downstream overwrite; a test that injects through the filtered channel; deletion of the downstream
overwrite leaves the suite green, because the upstream filter already intercepts the forged value
before the downstream layer is ever reached.

**Rule 3 (dimensional totality):** a mapping whose keys are normalized by a dedicated function before a
membership test; a case set that varies only the key's text; a mutation that moves the membership test
from the normalized key to the raw key — green, because no case supplies a key whose raw and normalized
forms differ. Executed on the real consumer artifact: `303 passed` before the remedy, `11 failed` after
a single case varying the key's *form* (not name) was added.

## Universality check

Independent of any local norm, project boundary, or language version: all three rules describe how a
test's case set, subject, and dimensional coverage relate to a specification versus an implementation
under test — a property of test construction, not of any one corpus's normative content. SFL-INV-08 is
met on both limbs: each rule carries its own deterministic, project-independent minimal reproduction,
and the nine occurrences span different files, different rounds, and two different actors finding them —
genuine independent recurrence, not one task's single instance repeated.

## Suggested fix (delta-sized)

Add the three-rule family above to `references/testing.md` §Hygiene as one guidance block (they are one
family — provenance/subject/dimension are all "chosen from the specification, never the artifact" — not
three unrelated bullets), with the deterministic reproductions as illustrative snippets so the rule is
checkable, not merely aspirational.

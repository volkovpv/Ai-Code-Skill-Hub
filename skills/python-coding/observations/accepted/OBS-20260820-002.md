# The decision order licensed a per-caller environment-variable name, and the copy follows the name

## Context (input)

A field report from a consuming project. At the consumer the record is a
normative conflict (class C5) — the project's own rule and this skill's
wording disagreed and the project's rule won locally — but its narrow core
is universal and transfers on its own evidence: it is a statement about
processes and environments, not about that project's principals.

The duplication survey's decision order lists the data a caller may
legitimately differ by when several occurrences of one shape are collapsed
into a parameterized factory. That list included "an environment-variable
key" unconditionally.

## Expected behavior

When the callers are separate processes, they read the same, role-named
variable and each process is handed its own value by whatever starts it.
A per-caller variable name should be named as the narrow exception it is —
one process legitimately holding two principals — rather than sitting in a
list of ordinary per-caller parameters.

## Actual behavior

Read literally, the list licenses a per-caller variable name in the
ordinary case. That is the specific step that licenses the copy the rest of
the file exists to prevent: once two names exist for one role, the resolver
that reads them has nothing left to be parameterized by, so it is copied
too, and the copy is then justified by the very rule meant to collapse it.

## Minimal reproduction

Project-independent. Two processes each connect to the same store as their
own principal. Follow the decision order literally and give each its own
variable name (`STORE_A_USER`, `STORE_B_USER`); the shared resolver now has
no shared name to read, so a second resolver module is written for the
second process, and a third for the third. Give both processes the same
role name (`STORE_USER`) and let the orchestrator supply each container its
own value, and one resolver serves both — with the principals still
separated, because separation was always by value and never by spelling.
Nothing in a credential-separation requirement anywhere speaks about
variable names.

## Universality check

The transferring core — when the callers are separate processes the
variable name is shared and the value is per process; a per-caller name is
warranted only where one process legitimately holds two principals — names
no project, principal, framework or document. Everything project-specific
in the report (which principals exist, which document names them) stays at
the consumer.

Two boundaries belong in the delta and are part of what makes it honest:
one process legitimately holding two principals (a runtime role beside a
maintenance/migration role, a provisioner seeding several accounts) is the
case that does warrant a second name; and where every process is started
from a single shared environment file, one name cannot hold two values —
that is a deployment gap to close before the collapse, not a naming rule.

## Suggested fix

Qualify the decision-order item in place so an author reading only the list
is not misled, and add one section stating the role-versus-caller rule with
both boundaries.

# A filter guarding an input a downstream parser also normalizes must decide with that parser's own normalization

## Context (input)

A field report from a consuming project's build (Reviewer-confirmed C3; `SFL-INV-08`
met on the reproduction limb, with an independent supporting occurrence of the same
principle from an unrelated task). An inbound-header deny-filter, placed in front of a
component that itself parses and normalizes the same header names, compared header
names with its own hand-rolled comparison rule instead of the downstream component's
normalization. The two disagreed on at least one input shape, so a header supplied in
that shape passed the filter's deny check while the downstream parser still recognized
and trusted it — a live inbound-trust bypass, measured twice in a row before the filter
was rewritten to call the downstream component's own normalizer directly.

## Expected behavior

No rule in this skill's security guidance states the general principle: when a
security-relevant filter/deny-list sits in front of a component that itself parses and
normalizes the same input, the filter's own comparison rule must either BE that
component's normalization, or be proven equivalent to it — otherwise the two can
disagree, and an input in the gap between them bypasses the filter while still reaching
the parser.

## Actual behavior

The reported filter reimplemented its own name-comparison instead of reusing the SDK's
own normalization function that the SDK applies when it later reads the same input. The
two comparisons disagreed on at least one input shape, producing a live bypass.

## Minimal reproduction

Deterministic, project- and language-independent (any guard placed in front of a
normalizing parser):

    DENY = {"sentry-trace", "baggage"}
    def is_denied(header_name: str) -> bool:
        return header_name.lower() in DENY          # filter's own rule

    def sdk_normalize(header_name: str) -> str:
        return header_name.lower().replace("_", "-").removeprefix("http-")  # parser's own rule

    # a header supplied as "HTTP_Sentry_Trace" (or any shape the filter's `.lower()`
    # alone does not reduce to "sentry-trace" but the parser's normalize() does) passes
    # `is_denied` == False while `sdk_normalize` still resolves it to the trusted name
    # the downstream parser accepts.

## Universality check

The repro above names no project identifier, no framework, and no domain-specific type.
It is a general statement about any filter-in-front-of-a-normalizing-parser pair, in any
language: the same shape applies to any deny-listed name space a downstream component
separately normalizes (HTTP header names, file extensions, MIME types, differently
quoted SQL identifiers). `SFL-INV-08`'s reproduction-limb threshold is met by the
deterministic, project-independent minimal reproduction above; the reporting project's
own occurrence count (two consecutive incidents on one subject, within one build) did
not by itself meet the occurrence-limb, but an independent occurrence of the same
general principle (a checker's own regex engine disagreeing with the enforcer's regex
engine on the same input) was separately observed in that project's history, supporting
the same underlying class.

## Suggested fix

Add a rule to the security guidance: a filter guarding an input that a downstream
component also parses and normalizes must decide using that component's own
normalization (call it directly, or prove equivalence), never a hand-rolled comparison
that can silently diverge from it. The concrete fix shape already demonstrated in the
reporting project's own closing change: replace the hand-rolled comparison with a direct
call to the authoritative parser/normalizer, not a second enumeration of cases.

## Context (input)

A field report from a consuming project's build. A port method taking two parameters gained a third. The unit spec asserted that a call never happened by listing the full old argument list: `expect(port.confirm).not.toHaveBeenCalledWith(RELEASE, 'item-1')`. The author updated the positive assertions of the spec for the new signature and left the two negative ones as they were. A reviewer found the stale assertions; the author did not.

## Expected behavior

`testing-discipline` says a test is not evidence until it has been seen red for its own reason (workflow step 3), and its interaction-precision rules (`references/unit-test-value.md`, "Match arguments only as precisely as the scenario constrains them") warn that an argument matched more tightly than the scenario needs is a false positive waiting for the next unrelated change. Both argue only one direction. Nothing says that a **negative call assertion pinned to a full argument list stops being able to fail the moment the callee's signature grows**, so that every such assertion must be re-derived (or loosened to the discriminating arguments plus a wildcard) whenever a signature changes. A rule was expected next to the "Match arguments only as precisely..." bullet.

## Actual behavior

Compiler and runner stayed green on the stale negative assertions: a call recorded with three arguments never equals an expected list of two, so the assertion passed whatever the code did. A mutant that performed the forbidden call after a failure left the suite fully green (22 of 22). Only a mutation probe aimed at that specific test exposed it; with the extra wildcard argument the same mutant turned the suite red (1 failed of 22).

## Minimal reproduction

Language-neutral, with any mock or spy library that matches calls by their whole argument list.

1. `function save(id) {}` and a test `assertNeverCalled(save, with: ['a'])`, run against code that never calls `save`. Red-first can be shown: a mutant that does call `save('a')` fails the test.
2. Change the signature to `save(id, payload)`. Update the real call and the positive assertions to pass two arguments; leave the negative assertion as `['a']`.
3. Mutate the code to call `save('a', x)` where it must not. The negative assertion still passes.
4. Fix: assert on the discriminating arguments and a wildcard for the rest, `assertNeverCalled(save, with: ['a', ANY])`. The mutant now fails it.

## Universality check

Independent of language, framework and test school: it holds for any mock or spy that compares a recorded call with an expected argument list, in unit tests of any project. It involves no project norm, threshold or version; the skill already owns the vocabulary (interaction precision, "seen red") and the fix is expressible in its own terms.

## Suggested fix

Next to the "Match arguments only as precisely..." bullet in `references/unit-test-value.md`, add the opposite direction: a negative call assertion can lose the ability to fail without any compile or run signal when the callee's signature changes, so each one is re-observed red (or reviewed) on such a change and written over the discriminating arguments plus a wildcard. One pointer sentence in the `SKILL.md` precision bullet.

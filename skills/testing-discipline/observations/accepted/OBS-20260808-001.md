## Context (input)

A field report from a consuming project's build of an async-service composition root.
A new composition function was added (nine unit tests of its own construction logic)
and mounted into the service's composition root with two lines: the call that builds
the module, and a callback that registers its teardown. No test asserted that the
mount itself happened. The two mounted lines were nonetheless reported "covered" by
the merge-gate coverage lane, because a pre-existing test that boots the real startup
path for an unrelated reason (asserting an unrelated queue-prefetch wiring) runs the
real composition root and therefore executes both lines as a side effect on its way to
an assertion about a different collaborator entirely.

## Expected behavior

`testing-discipline` rule 12 ("Exercise the production wiring, not a hand-built copy of
it") and the coverage guidance in `references/hygiene.md` ("a healthy mutation score is
not evidence of specification coverage"; "use coverage to find untested areas, not as a
target") both approach this shape from adjacent angles, but neither states the rule
that would have caught it: for a line whose entire content is a wiring/DI decision (a
call to a factory, a registration of its result), execution-count coverage is not
evidence of protection — only a targeted mutation of that exact line (delete it, or
swap its argument) is, because such a line has no return value of its own for an
assertion to examine and is trivially satisfied by any caller that happens to reach it
for an unrelated reason.

## Actual behavior

Neither rule 12 nor the hygiene coverage guidance named this failure mode. Rule 12
stated the direction of the fix generally ("exercise the production wiring") but did
not distinguish "executed by the production wiring" from "asserted about the
production wiring" — the two collapse in the coverage report, which is exactly what
happened here: the pre-existing test does exercise the real composition root,
satisfying rule 12's letter, while making no claim whatsoever about the two lines under
discussion. The hygiene guidance warns against treating coverage as a target and
against a mutation score standing in for specification coverage, but did not name the
narrower, common case of a single wiring/DI line inside an otherwise well-tested
composition root.

## Minimal reproduction

Project-independent by construction — no plane fixture, language runtime, or DI
framework is required beyond "a composition root with an existing wiring test and a
new wiring line added alongside it":

1. In any composition root / entry point that already has ONE test exercising its real
   startup path for an unrelated reason (e.g. asserting a resource limit, a route, a
   header), add a new line that constructs a collaborator via a factory and
   stores/registers it, with no other observable effect.
2. Run the existing test suite and the coverage tool. Observe the new line reported as
   covered.
3. Delete the new line. Re-run the suite. Observe no test goes red.
4. Consult `testing-discipline` rule 12 and the hygiene coverage guidance while
   deciding whether the change from step 1 needs its own test. Observe that neither
   rule, read literally, flags step 3's outcome as a defect — the line was "exercised
   by the production wiring" (rule 12's own phrasing) the whole time.

A deterministic instance of the same mechanism was independently produced by the
consuming project's own Reviewer: deleting a per-match observability emission (a
`logger.info` call, its structured context and its payload) from an unrelated
production module left 1343 of 1343 unit tests green at 97.59% line / 91.32% branch
coverage, while a sibling emission in the same file *is* asserted by a test.

## Universality check

Nothing above depends on any particular language, test runner, dependency-injection
mechanism, or architectural layering convention. The trap — a coverage tool measuring
*execution*, a wiring line having no return value or side effect of its own to assert
on, and an unrelated pre-existing test incidentally reaching it — recurs in any
composition root, in any language, under any test runner that reports line/branch
coverage. `testing-discipline` already declares itself universal and already carries
adjacent rules (12, and the hygiene coverage section) that a maintainer would
reasonably expect to cover this case and did not. Five independent occurrences were
recorded across five consecutive tasks in the reporting project, in at least two
distinct modules, at least one of them a deterministic, project-independent
reproduction rather than a naturally occurring instance.

## Suggested fix (optional)

Add one clause to rule 12 (or a short paragraph in `references/isolation-and-fakes.md`,
which already owns "testing construction or an outgoing call") stating the *direction
of evidence* for a pure wiring/DI line specifically: coverage produced by a test that
asserts something else is not protection; the regression check is a targeted
fake/spy at the collaborator's construction seam, asserting both the call (with its
expected arguments) and, where the mounted resource owns teardown, that the teardown
is registered.

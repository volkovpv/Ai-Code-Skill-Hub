## Context (input)

A field report from a consuming project's build. Six pre-existing integration-test
suites for a persistence adapter were, for the first time, run against a real, shared,
long-lived datastore instance (not a per-suite disposable one). Every one of them
followed `testing-discipline`'s own persistence rule literally: clean the store at the
start of each test (a plain unconditional table-wide DELETE/TRUNCATE in the suite's
setup step), never at the end. Doing so against a store the suite does not exclusively
own destroyed pre-existing, non-fixture rows on every run — rows the suite never
created and had no right to erase, including administrative/configuration data another
part of the same system depended on.

## Expected behavior

`references/adapters-and-persistence.md`, "Clean persistent state at the *start* of a
test, not at the end": *"The runner cannot isolate tests from data that outlives them,
so the fixture must. Do it on the way in."* The rule and its comparison table
("Isolation: the next test cleans before it runs" / "clean at the end … broken as soon
as a test fails before its cleanup") are written, and read, as if the persistent store
in question is scoped to the suite — every consequence it draws is true only under
that premise. The rule states no precondition that the store must be OWNED (exclusively,
or at least partitioned) by the suite doing the cleaning, and gives no guidance for the
case where it is not.

The gap is sharper than a missing precondition: `references/schools.md`, in the SAME
skill, already defines the exact archetype the cleanup rule silently assumes away —
**Shared dependency** ("one that two tests can both reach and through which one test can
change another's result — a mutable global, a database"), **Out-of-process dependency**
("Usually shared, but not necessarily — a per-test container instance … is
out-of-process and private"), and **Unmanaged dependency** ("an out-of-process
dependency whose side effects other applications can see … a broker, a mail server, a
shared table"). `schools.md`'s own "three consequences hold under either school" list
draws a consequence from the shared/private distinction for exactly one thing —
whether a dependency can be re-created per test instead of being replaced (doubling) —
and never for cleanup, even though the cleanup rule lives in the same skill and the
same distinction governs it just as directly.

The immediately following section of the same file, "Make transaction boundaries
explicit; do not isolate by rolling back", removes the one mechanism that would have
made "clean at the start" safe by construction over a shared store without a hand-built
capture/restore protocol: transactional rollback isolation. Its own stated reasons
("commit is where the work happens", "rolling back destroys the evidence of a
failure") are correct for an owned store and simultaneously close the only cheap escape
hatch for the shared-store case, without naming a replacement for it.

## Actual behavior

A literal, correct-per-the-rule-as-written application of "clean at the start" over a
single, long-lived, shared datastore instance produced repeatable destruction of
pre-existing data on every suite run, in six independent files following the same
pattern, plus a second, independent, PRE-EXISTING file (from an earlier, unrelated
task) that had already discovered the same gap on its own and hand-rolled a
capture-then-restore-by-value workaround for one table, rather than following the rule
as written, because the plain form was unsafe over the shared store.

## Minimal reproduction

Project-independent shape:

```
# Given: a persistence-adapter/integration test suite whose fixture cleanup follows
# "clean persistent state at the start of a test, not at the end" as testing-discipline
# states it — a plain DELETE/TRUNCATE/equivalent of the whole table(s) it touches, run
# in the suite's setup step, no rollback-only isolation (per the same file's own
# second rule).
#
# When: that suite is pointed at a datastore instance it does NOT exclusively own — a
# shared dev/CI/staging database, a schema also used by another suite or by a human
# operator, any store outside the suite's own private, disposable scope.
#
# Then: the very first test run silently deletes every pre-existing row of every table
# the fixture "cleans", because the rule instructs cleaning the table, not the suite's
# own rows — and gives no test-side primitive (capture, scope, ownership check) to tell
# the two apart.
```

No project-specific fixture, table name or ID is required to reproduce the shape —
only "a shared, non-exclusively-owned persistent store" and "clean-at-the-start with no
rollback isolation", both drawn from the rule's own two sections.

## Universality check

`testing-discipline` is explicitly project-agnostic by its own contract ("no
ecosystem, no mocking library"), and the gap is in the rule's own stated scope, not in
any project-local convention. Any project whose integration tests run against a real,
shared, long-lived datastore — which the skill itself explicitly scopes integration
tests to reach — meets the same gap the same way. The skill already owns the
vocabulary (`schools.md`'s Shared/Out-of-process/Unmanaged dependency archetypes) that
would have prevented it; the fix is expressible entirely in the skill's own existing
terms and introduces no new vocabulary.

## Suggested fix

State the ownership precondition explicitly in "Clean persistent state at the start of
a test, not at the end", using `schools.md`'s own vocabulary: the rule as written
applies to a store the suite exclusively owns (a **private** dependency); where the
store is instead the **shared** or **unmanaged** archetype, name the alternative the
neighbouring rule forecloses (transactional rollback) as unavailable and name the
required substitute — privatize the store (a disposable schema/database/container per
suite or per run), or scope the cleanup to rows the suite itself owns (capture-by-value
before mutating, restore-by-value after, or a tagged-ownership convention) — with the
same rigor `adapters-and-persistence.md` already gives the owned-store case. Extend
`schools.md`'s own "consequences" list so the shared/private distinction is drawn for
cleanup, not only for doubling, closing the gap at its source rather than only at its
symptom.

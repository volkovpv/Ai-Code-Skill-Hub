# The cycle: when a test exists relative to the code

Every other file in this skill judges a test once it exists. This one is
about *when* it exists — one test, one unit.

Its first section holds in any project, whatever process it follows. The
rest describes **test-driven development** and applies where the host
project declares that it practises it — declared the same way the school
is, see [schools.md](schools.md). Where the project has not declared it,
none of the cycle is imposed; the evidence rule below still is.

## Holds regardless of process: a test is not evidence until it has been red

**A test that has never been observed to fail is not yet evidence of
anything.** Until you have seen it red *for the reason it names*, it is
itself untested: it may assert nothing, may address the wrong subject,
may never have been collected by the runner at all. A green run over such
a test reports only that nothing crashed.

- Writing the test first satisfies this for free — the first run is red,
  and the red run is the measurement, not a formality.
- Writing the test after the code costs one extra step: break the
  behaviour the test names — revert the fix, invert the condition, delete
  the guard — watch the test go red, restore. That step is the whole
  difference between a test and a decoration.
- **Watch which failure you got.** A test red because its arrange step
  blew up, or because a name is missing, has demonstrated nothing about
  its assertion. The red you need is the assertion's.
- **An unexpected green is information, never a relief.** A test you
  expected to fail and which passes means the behaviour already exists,
  the test is not reaching the subject, or you misunderstand the
  mechanism. All three are worth the minutes it takes to find out; each
  of them silently invalidates the test if you do not.

## The two rules

Everything below is generated by two:

1. **Write a failing automated test before writing any production
   code.**
2. **Remove duplication.**

The loop that follows from them:

| Step | | Exit condition |
|------|---|----------------|
| 1 | Add one small test | it is written, not yet run |
| 2 | Run every test | the new one fails, for its own reason |
| 3 | **Read the failure message; improve it if it does not explain itself** | it would tell a stranger what is wrong |
| 4 | Make the smallest change that passes it | nothing else changed |
| 5 | Run every test | all green |
| 6 | Refactor to remove duplication | green after each step |

**Step 3 is not optional and does not belong later.** It happens while
the failure is in front of you and before any production code exists,
because a failure you cannot read is a test that will be deleted the
first time it fires under deadline — and because an intention you cannot
state in a failure message is one you have not finished forming. See
[test-diagnostics.md](test-diagnostics.md).

Two constraints on the loop itself:

- **Never more than one red test at a time.** Conservative climbers keep
  three of four limbs attached; two red tests mean two suspects and
  nothing to bisect against. When a test turns out to require several
  changes at once, it was too big — park it, write the smaller test that
  covers the one part that is broken, and reintroduce the larger one.
- **A green bar is a place you can stand.** Reaching green with code you
  intend to delete in the next minute is progress; staying red while you
  reach for the design you want is not.

## The refactor step

- **Duplication between the test and the production code counts.** It is
  what a deliberately constant first implementation leaves behind, and
  removing it is what turns that constant into the general case.
- **Faking it is not tuning a test to the gate.** The constant goes into
  the *production* code, it is transient, and the refactor step removes
  it by eliminating the duplication between the test's literal and the
  code's; the test is never touched. Choosing a value *in the test*
  because it turns a red run green is the opposite move and stays
  forbidden — see [hygiene.md](hygiene.md).
- **Refactoring here preserves semantics with respect to the tests you
  have** — which is a licence to move quickly and an obligation to have
  enough of them. "The tests all passed" is not an answer to "I knew
  there was a problem in there."
- **Unify two similar pieces by making them identical first, and merge
  them only once they are.** A refactoring that requires a long chain of
  reasoning about control flow to believe is exactly the kind this loop
  exists to avoid.
- Refactoring is also how coverage improves without new tests: the same
  cases over simpler logic cover more of it.

## What the cycle owes the rest of the discipline

- **Before the first use of an unfamiliar external facility, write a test
  against it** rather than against your code — you learn the interface
  and you gain a pinned statement of what it does, which is the same
  evidence the fake-provenance rule demands. Re-run those tests on every
  upgrade of that dependency: if they fail, there is no point running the
  application. See [isolation-and-fakes.md](isolation-and-fakes.md).
- **Every defect starts with the smallest test that reproduces it**, and
  then with one further question: *how could I have known to write this
  test in the first place?* The answer names a category — integer
  overflow, an empty collection, a duplicate key — that belongs on every
  future test list. A regression suite that never feeds back into how
  tests are chosen keeps buying the same lesson.

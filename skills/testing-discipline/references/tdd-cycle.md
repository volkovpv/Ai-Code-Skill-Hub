# The cycle: when a test exists relative to the code

Every other file in this skill judges a test once it exists. This one is
about *when* it exists, and about the loop that produces the test and the
code together.

Its first section holds in any project, whatever process it follows. The
rest describes **test-driven development** and applies where the host
project declares that it practises it — declared the same way the school
is, see [schools.md](schools.md). Where the project has not declared it,
none of the cycle is imposed; the evidence rule below still is.

## Holds regardless of process: a test is not evidence until it has been red

**A test that has never been observed to fail is not yet evidence of
anything.** Until you have seen it red *for the reason it names*, it is
itself untested: it may assert nothing, may address the wrong subject,
may never have been collected by the runner at all. A green run over such
a test reports only that nothing crashed.

- Writing the test first satisfies this for free — the first run is red,
  and the red run is the measurement, not a formality.
- Writing the test after the code costs one extra step: break the
  behaviour the test names — revert the fix, invert the condition, delete
  the guard — watch the test go red, restore. That step is the whole
  difference between a test and a decoration.
- **Watch which failure you got.** A test red because its arrange step
  blew up, or because a name is missing, has demonstrated nothing about
  its assertion. The red you need is the assertion's.
- **An unexpected green is information, never a relief.** A test you
  expected to fail and which passes means the behaviour already exists,
  the test is not reaching the subject, or you misunderstand the
  mechanism. All three are worth the minutes it takes to find out; each
  of them silently invalidates the test if you do not.

## The two rules

Everything below is generated by two:

1. **Write a failing automated test before writing any production code.**
2. **Remove duplication.**

The loop that follows from them:

| Step | | Exit condition |
|------|---|----------------|
| 1 | Add one small test | it is written, not yet run |
| 2 | Run every test | the new one fails, for its own reason |
| 3 | Make the smallest change that passes it | nothing else changed |
| 4 | Run every test | all green |
| 5 | Refactor to remove duplication | green after each step |

Three constraints on the loop itself:

- **It is minutes long, not hours.** Its length is the variable you
  control — see *step size* below.
- **Never more than one red test at a time.** Conservative climbers keep
  three of four limbs attached; two red tests mean two suspects and
  nothing to bisect against. When a test turns out to require several
  changes at once, it was too big — see *Child Test* below.
- **A green bar is a place you can stand.** Reaching green with code you
  intend to delete in the next minute is progress; staying red while you
  reach for the design you want is not.

## The test list

**Before starting, write down every test you know you will have to
write.** Then work the list instead of holding it in your head.

- Seed it with an example of each operation you know you need, the
  degenerate (do-nothing) variant of each operation that does not exist
  yet, and the refactorings you already expect to owe.
- **Implement one at a time.** Writing them all up front means a long red
  bar and a pile of inertia against the refactoring you have not done yet.
- **New ideas go on the list, not into the current change.** A tangent
  that arrives mid-loop — a case you had not considered, an ugliness you
  noticed — is written down and the loop continues. This is what keeps a
  session from turning into an unbounded search.
- **Items left at the end of a session are not free.** Finish them, or
  move them deliberately to a later list. A test case that might not pass
  is worth more than shipping today's change; an out-of-scope refactoring
  is not.

## Choosing and sizing the next test

- **One step at a time.** From the list, pick the test that teaches you
  something *and* that you are confident you can make pass. The ones that
  are obvious teach nothing; the ones you have no idea about buy a long
  red bar. If nothing on the list qualifies, add smaller tests that get
  you closer to the ones that do.
- **Start with a degenerate case.** The first test for a new operation
  should answer only *where does this belong?* — so give it inputs and
  outputs that are trivially easy to know: the empty input, the single
  element, the case where the output equals the input. A realistic first
  test asks you to solve placement, input and expected output at once,
  and leaves you without feedback for far too long.
- **When a test turns out to be too big, replace it with a smaller one.**
  Delete (or park) the oversized test, write the test that covers the one
  part that is broken, get that green, then reintroduce the larger test.
  Ask why it was too big — the answer usually names a missing step on the
  list.
- **The direction is known-to-unknown, not top-down or bottom-up.** A
  program grown this way looks top-down from one angle (the first test
  states a simple case of the whole operation) and bottom-up from another
  (small pieces aggregating). Neither metaphor predicts anything useful;
  "start where you have knowledge and grow toward where you do not" does.

## Getting to green: four gears

Once a test is red, reaching green is a separate problem from reaching a
design you like. These are the ways to make the crossing, ordered from
the largest step to the smallest:

| Gear | What you type | Use it when |
|------|---------------|-------------|
| **Obvious implementation** | the real thing, directly | you know what to type and can type it quickly |
| **One to many** | implement for a single element first, then generalize the parameter to a collection | the operation's subject is a collection |
| **Triangulate** | a second, differing example, which forces the abstraction | you do not trust yourself to see the right abstraction from one case |
| **Fake it** | return a constant, then turn the constant into an expression by removing the duplication between test and code | you do not know what to type at all |

- **Downshift on surprise.** Track how often a red bar surprises you
  under obvious implementation. Often surprised → drop a gear. Never
  surprised and bored → take bigger steps. Demanding the top gear of
  yourself always is how a loop stalls.
- **Triangulate sparingly.** Its rule is crisp — abstract only with two
  examples — but taken literally it loops forever: once the abstraction
  is in, one of the two examples is redundant, and deleting it licenses
  collapsing the code back to a constant. Use it for the calculations you
  genuinely cannot see through, not as a default.
- **Faking it is not tuning a test to the gate.** The constant goes into
  the *production* code, it is transient, and the refactor step removes it
  by eliminating the duplication between the test's literal and the
  code's; the test is never touched. Choosing a value *in the test*
  because it turns a red run green is the opposite move and stays
  forbidden — see [hygiene.md](hygiene.md).

## Step size is the variable, not a virtue

The discipline is not "small steps"; it is **awareness of the gap between
a decision and the feedback on it, and deliberate control of that gap.**
A week of paper design followed by test-driven code is within the
discipline if the gap was chosen. Reflexively taking the largest step you
can get away with is not.

The heuristic: **the harder the problem, the less ground each test
covers.** Tests are the teeth of a ratchet — the heavier the bucket, the
closer together the teeth need to be.

## The refactor step

- **Duplication between the test and the production code counts.** It is
  what a faked implementation leaves behind, and removing it is what
  turns the fake into the general case.
- **Refactoring here preserves semantics with respect to the tests you
  have** — which is a licence to move quickly and an obligation to have
  enough of them. "The tests all passed" is not an answer to "I knew
  there was a problem in there."
- **Unify two similar pieces by making them identical first, and merge
  them only once they are.** A refactoring that requires a long chain of
  reasoning about control flow to believe is exactly the kind this loop
  exists to avoid.
- Refactoring is also how coverage improves without new tests: the same
  cases over simpler logic cover more of it.

## What the cycle owes the rest of the discipline

- **Before the first use of an unfamiliar external facility, write a test
  against it** rather than against your code — you learn the API and you
  gain a pinned statement of what it does, which is the same evidence the
  fake-provenance rule demands. Re-run those tests on every upgrade of
  that dependency: if they fail, there is no point running the
  application. See [isolation-and-fakes.md](isolation-and-fakes.md).
- **Every defect starts with the smallest test that reproduces it**, and
  then with one further question: *how could I have known to write this
  test in the first place?* The answer names a category — integer
  overflow, an empty collection, a duplicate key — that belongs on every
  future test list. A regression suite that never feeds back into how
  tests are chosen keeps buying the same lesson.
- **Explain in tests.** Asking "so if the input is this, the answer
  should be that?" and answering the same way is the cheapest way to
  discover that two people are solving different problems.

## Ending a session

| Situation | Leave it | Why |
|-----------|----------|-----|
| Working alone, nothing to share yet | with the last test written and **failing** | it is a bookmark: you resume by reading a concrete, unfinished thought instead of hunting for where you were |
| Anything you share — a commit, a push, a review | with **everything green** | whoever picks it up must start from certainty about what works |

The broken test above lives in the working copy and nowhere else.
Sharing a red suite, or silencing a test to make the suite pass, is the
hygiene rule and it always wins — see [hygiene.md](hygiene.md).

## Where the cycle does not reach

- **Security and concurrency.** Passing tests cannot demonstrate that the
  goal was met: security rests on human judgment about the method chosen,
  and a subtle race is not reliably reproduced by running the code.
- **Performance, stress and usability.** The suite this loop produces is
  worth keeping for as long as the system runs, and it replaces none of
  these.
- **A design decided in advance.** Choosing the pattern first and writing
  the second test in order to force the code into it mostly produces
  surprise: sensible-looking design ideas turn out to be wrong under the
  actual cases. State what the system should do; let the design follow.
- **Existing code with no seams.** Do not stop delivery to test and
  refactor everything — the deadlock between "cannot refactor without
  tests" and "cannot test without refactoring" is broken by limiting
  scope to what must change now, and by accepting coarser feedback
  (careful work, a second pair of eyes, system-level tests known to be
  inadequate) while that area becomes testable.

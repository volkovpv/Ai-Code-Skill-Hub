## Context (input)

Same defect family as `skills/python-coding/observations/accepted/OBS-20260727-001.md`,
transferred a second time onto `typescript-coding` because the gap is a property of how a
test double's contract is established, not of any one language's standard library. The
original three occurrences were found in a Python consumer build (`news-intel-docs`,
RM-TASK-017: AMQP client + idempotent consumer/manual-ack/DLQ + LangGraph checkpoint
store): in every one, a unit-test fake for a third-party seam — the RabbitMQ broker, the
SASL-PLAIN encoder underneath it, and a PostgreSQL driver's row factory — stayed green
while encoding a belief about that system's runtime behaviour that was simply wrong, and
only a live probe against the real system (never a re-reading of the project's own norm or
the vendor's documentation) ever caught it. Full evidence trail in the consumer's
`harness/review/skill-triage-2026-07-26.md` §2 (verdict C3, both threshold limbs
independently re-verified by the Reviewer's own execution).

The mechanism reproduces identically in TypeScript, because it is a mechanism of evidence,
not of syntax: the same brokers, encoders and database drivers are reached from Node
through `amqplib`/`node-postgres` instead of `aio-pika`/`psycopg`, the WHATWG `URL` parser
loses an empty username exactly as `yarl` does, and an object-row driver collapses
identically-named columns exactly as `dict_row` does.

`skills/typescript-coding/references/testing.md` already told the reader *what* to fake
("Mock **interfaces and seams the code exposes**, never someone else's internals") and was
silent on *how the fake's own return values become known to be true* of a system the
project does not own — confirmed by inspection of the pre-change file: neither "observ",
nor "probe", nor "real system" appears anywhere in it. The gap is not a coding mistake and
not a project-local norm question.

## Expected behavior

**A fake's own return values, when the property under test belongs to an external system,
are established by observing that system once, never by reading.** When the subject is a
message broker, an authentication encoder, a database driver's row shape, or any other
third-party system the project does not own, no fake, and no re-reading of a project norm,
an RFC, or vendor documentation, can establish what that system actually does — only a live
observation against the real system can. Write the fake only after a probe against the real
system has pinned the behaviour, then reuse that pinned observation as a fixture rather than
re-deriving it from prose on every subsequent change. Operational trigger: treat a second
rejection of the same reading on the same external-system property as the signal to switch
evidence class from reading to a live observation, not as cause to produce a third reading.

## Actual behavior

`skills/typescript-coding/references/testing.md`, pre-change, has no clause reaching the
provenance of a fake's return values; its nearest rule ("Mock interfaces and seams the code
exposes, never someone else's internals") is about the *shape* of the double — which layer
it stands in for — and says nothing about the *content* it hands back.

First-upstream-failure summary of the three source occurrences, one per external system:

1. **Broker (AMQP)** — the event name was taken from a routing key. The broker rewrites the
   delivery key at every dead-letter hop while carrying the message `type` through
   unchanged. Two consecutive fix rounds each picked a different key by re-reading the
   project's own routing-key convention doc; a unit-test fake for the publisher port
   encoded whichever wrong belief was current and stayed green throughout — only a live
   two-hop TTL/DLX probe against the real broker settled it.
2. **Authentication encoder (SASL-PLAIN)** — a non-blank check at the settings layer looked
   sufficient by reading the code path one layer up. The encoder substitutes a default
   identity for a username that is absent **or empty**, one layer below the wrapper under
   test; no fake at the wrapper's own seam could see this, because the fake's job was to
   stand in for the very layer that does the substitution.
3. **Database driver row shape** — two un-aliased boolean columns collapse into a single key
   under an object-row factory, so the fetched row was a one-item mapping. The unit-test
   fake for the schema-check cursor was written with both properties present — the ordinary
   expectation, and exactly wrong for a connection opened in object-row mode. Only a live
   query against the real database produced the failure.

## Minimal reproduction

Two of the three occurrences reduce to a deterministic, project-independent, self-contained
snippet in TypeScript/Node idiom; the third (a live two-hop broker DLX cycle) is not
reducible to one, which is itself part of what this observation is about — a
topology-dependent broker behaviour of this kind cannot be established by reading the
AMQP 0-9-1 spec prose either, only by observing the pinned broker version.

- `new URL("amqp://:p@h:1").username` is `""`, indistinguishable from the absent user of
  `new URL("amqp://h:1")`, whose `username` is also `""` — so whatever client library reads
  that URL is free to substitute its own default identity. Executed here on Node v26.4.0:
  both forms yield `""`, while `password` is `"p"` and `""` respectively. Same behaviour as
  the source observation's `yarl.URL.build(..., user="")` reproduction, in the WHATWG URL
  parser.
- PostgreSQL names an unaliased expression column `?column?`, so `SELECT true, false`
  returns two identically-named fields and an object-row driver collapses them into a
  one-key row (`{ "?column?": false }`), while `SELECT true AS a, false AS b` returns both.
  The PostgreSQL-side fact is the source observation's reviewer-executed evidence against a
  live PostgreSQL 18.4 instance (`{'a': True, 'b': False}` vs `{'?column?': False}`); the
  collapse follows deterministically for any driver that builds rows as objects keyed by
  column name, and an array row mode is the driver-side escape hatch.

## Universality check

Independent of any local norm, project boundary, or language: the subject in all three
occurrences is the behaviour of a third-party system this project does not control and did
not write — a broker, an authentication encoder, a database driver's row shape — and the
rule describes which class of evidence can establish such behaviour, not any one language's
syntax. SFL-INV-08 is met via the deterministic, project-independent minimal-reproduction
limb: the source observation's 3 independent occurrences and 2 reviewer-re-executed
reproductions carry over, and the URL reproduction was re-executed here in TypeScript/Node
idiom.

## Suggested fix (delta-sized)

Mirror the `python-coding@1.3.0` `references/testing.md` guidance block, adjacent to the
existing mock-the-seam rule, with reproductions restated in TypeScript idiom: the reference
behaviour a fake encodes for an external system is established once, by observing the real
system, and pinned as a fixture — never assumed from project-normative prose, vendor
documentation, or a second reading of either after a first reading was already rejected,
with the second-rejection-switches-evidence-class operational trigger. Ship both
reproductions above as the rule's illustrative snippets so it is checkable, not merely
aspirational.

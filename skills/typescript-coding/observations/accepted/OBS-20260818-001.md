# The cited duplication rule list cannot see cross-file or renamed duplication

## Context (input)

A field report from a consuming project's build (Reviewer-confirmed C3;
`SFL-INV-08` met on both limbs). The project's own tree measured a large
class of duplicated production-code implementations that its actually
configured tooling did not report: a rename-tolerant structural detector
found roughly half of production tokens inside a clone class, a
text-identical detector found a much smaller fraction, and the project's own
duplication tool reported almost none, with zero findings in the single
most-affected directory. Tracing the gap back to this skill's own guidance
found the cause: the "No magic, low duplication, low complexity" section
names four SonarJS/ESLint rules and stops at "factor the shared body out",
with no statement of what those rules actually cover.

## Expected behavior

A skill whose duplication guidance is meant to prevent this class of defect
would either name the scope limit of the cited rules explicitly (same-file
only, textual-identity only, no rename tolerance) so an implementer does not
mistake a green lint run for the absence of cross-file duplication, or state
the obligation at the level that actually matters: an identical
implementation has exactly one home regardless of which file it lives in.

## Actual behavior

The section names four rules and stops, with no statement of scope. Every
one of the four — `no-all-duplicated-branches`, `no-duplicated-branches`,
`no-identical-conditions`, `no-identical-functions` — operates within a
single file by the rule's own design, and none is tolerant of identifier
renaming. Re-executed against `eslint` 10.7.0 + `eslint-plugin-sonarjs`
4.2.2 (`--no-config-lookup`, no project configuration) on a four-file
scratch tree:

| placement | rename | `no-identical-functions` |
|---|---|---|
| same file | none (exact copy) | fires, exit 1 |
| same file | renamed | 0 findings |
| different files | none (exact copy) | 0 findings |
| different files | renamed | 0 findings |

Only the first row is caught. The rule family exposes no cross-file check
of any kind, and identifier renaming alone silences it even within a single
file — a strictly wider blind region than "cross-file only" would suggest.
A project whose only duplication discipline is this skill's guidance has a
false sense of coverage, not merely a missing rule.

## Minimal reproduction

Deterministic, project-independent (any TypeScript/ESLint project following
this skill's stack):

1. `a.ts`: `export function computeX(value: number): number { return value * 2 + 1; }`
2. A different module, `b.ts`: `export function deriveY(input: number): number { return input * 2 + 1; }`
   (identical body, function and parameter renamed).
3. Run ESLint with `eslint-plugin-sonarjs`'s `no-identical-functions` enabled
   exactly as this skill's guidance configures it. Result: zero findings.
4. Control (same file, same rename): confirms the rule fires on an exact,
   unrenamed duplicate in the same file — the one case it is designed to
   catch — and that step 3's silence is the rename/file boundary, not a
   misconfiguration.
5. Control (different files, no rename): also zero findings — the boundary
   the rule cannot see is the file, independent of any rename.

## Universality check

Nothing above depends on this project's rules, its stack version, or its
file layout — only on the documented scope of the four rules `lint-clean.md`
itself cites and on ESLint/`eslint-plugin-sonarjs` as installed per this
skill's own configuration guidance. `SFL-INV-08`'s first limb is met by
several independently occurring, differently-typed clusters measured on the
reporting project's own tree, introduced across unrelated tasks weeks apart
(not one census recounted several ways); its second limb is met by the
reproduction above, which needs no project file to run.

## Suggested fix

State the scope of the four cited rules directly after naming them (same-file,
textual-identity only, no rename tolerance) and add the obligation the
census shows actually matters: an identical implementation has exactly one
home regardless of which file it lives in.

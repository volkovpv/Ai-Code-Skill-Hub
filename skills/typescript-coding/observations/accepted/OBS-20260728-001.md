## Context (input)

Same defect family as `skills/python-coding/observations/accepted/OBS-20260728-001.md`
(python-coding `1.3.0 -> 1.4.0`), transferred a second time onto `typescript-coding`
because both sub-shapes are properties of *where a test collects its evidence*, not of
any one language. The source is a field report from a consuming project's build of a
thin adapter around a third-party SDK client, where two related gaps recurred in the
same build after the Hub fix for the adjacent "external-system fake contract" class
(this skill, `references/testing.md` "A fake's own return values ... are established by
observing that system once", OBS-20260727-001) was already pinned:

1. An outbound-mutation gap: a request-metadata value the caller does not fully
   control (a header, id, or default the third-party client regenerates on every
   call) was never verified to reach the wire, because every unit test faked the
   exact SDK layer that would perform (or fail to perform) that substitution. The
   pinned rule's own scope sentence — "a fake's own return values" — describes an
   output-side property (the fake computing a wrong value for a given input); this
   defect has no return value to inspect at all, so a reader keying on that scope
   sentence would not recognise the shape as covered.
2. A wiring-level gap: every test that asserted a property of how the third-party
   client was constructed (which arguments, which interceptors) built its own copy
   of that client inside the test, rather than exercising the production factory
   that is the sole place the real construction happens. Removing the argument
   under test from the production factory left the full suite green, because no
   test exercised that code path at all.

Inspection of the pre-change `skills/typescript-coding/references/testing.md` confirms
the same silence there: the file carried the parent external-system rule but neither
sub-shape — no clause about a value substituted on the way OUT of a call, and none
about which seam a construction/wiring assertion must be taken at.

## Expected behavior

The skill's existing external-system guidance already establishes that a fake's
return values, for a property belonging to an external system, must be pinned by a
live observation rather than by reading. It does not extend that duty to (1) a
value the real layer substitutes on the way OUT of a call, where there is no return
value to inspect, or to (2) the construction of the collaborator itself, where a
test that builds its own instance proves the property achievable but never that the
product's own wiring achieves it.

## Actual behavior

Both gaps shipped past a green suite. In case 1, the fake replaced exactly the layer
that would perform the substitution, so no assertion could distinguish "the value
reaches the wire" from "the value is silently dropped". In case 2, the production
wiring point for the third-party client had no test coverage at all; a test built
its own client instance and asserted a property of that hand-built object, which
establishes nothing about what the product's own factory does.

## Minimal reproduction

Both reproductions are language-neutral; restated here in TypeScript/Node idiom.

1. Outbound-mutation shape: take any third-party client whose outgoing call sets its
   own request-id, retry token, or default identity header regardless of what the
   caller passes (a common shape in HTTP/gRPC SDKs whose own interceptor regenerates
   a client-supplied trace/correlation id). Write a unit test that replaces the
   client's request-sending method with a `jest.fn()` (or any recording double)
   capturing only the call's own arguments. The test stays green whether or not the
   caller's value ever reaches the header the caller cares about, because the
   property under test is never exercised by anything the double can see.
2. Wiring-level shape: a `createClient(...)` factory is the sole production place the
   `interceptors` / `hooks` option is assembled. Every test builds its own client
   object with its own interceptor array instead of calling the factory. Removing
   that option from the factory call leaves the full suite green, because no test
   exercises the factory's own construction.

## Universality check

Both sub-shapes are language- and library-neutral: any client library with a
seam that substitutes a value the caller does not fully control on the way out
of a call exhibits shape 1; any project with a factory/DI wiring point for a
third-party collaborator can exhibit shape 2 if every test constructs its own
collaborator instead of exercising that wiring point. Six occurrences of the
same underlying root ("evidence collected somewhere other than where the
property lives") were recorded across two consecutive tasks in the reporting
project, three of them after the adjacent fix for the sibling class was
already pinned and active — two independently-resourced reviewing actors in
that project each missed the wiring-level sub-shape on a first pass, which the
reporting project's reviewer records as a legibility defect in the existing
rule's scope sentence rather than an application error. Neither limb depends on
Python: an options-object factory and an interceptor array are the same
construction seam in a Node project, and the substituting layer is the same
layer whichever SDK performs it.

## Suggested fix (delta-sized)

Mirror the `python-coding@1.4.0` `references/testing.md` delta: widen the existing
external-system bullet's scope so the outbound-mutation shape is named in place
(there is no return value to inspect; the belief needing a live observation is that
the caller's argument reaches the wire unmodified), and add one adjacent bullet for
the wiring-level rule (a construction/wiring assertion is taken at the production
factory, never at a hand-built instance), each with its minimal reproduction restated
in TypeScript idiom. No pre-existing pinned clause is removed or altered.

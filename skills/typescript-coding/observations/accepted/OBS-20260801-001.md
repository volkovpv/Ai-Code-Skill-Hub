## Context (input)

A field report from a consuming project, raised as a side finding while the skill
was in use: a `@typedef` block had been written with `//` line comments, which is
inert for TypeScript — only a two-asterisk `/** */` block is read as JSDoc. The
reporter classified it explicitly as a real defect rather than a style deviation,
and as generalizable beyond the edit it was found in.

Inspection of the pre-change skill confirms the silence. `references/lint-clean.md`
§"JSDoc on the public surface" carried two rules — which symbols must carry a block
with a prose description, and that types must not be restated in it — and said
nothing about the one form in which a block is parsed at all. `knowledge/pitfalls.md`
had no entry for it, and the failure mode fits that file's definition exactly: a
construct that looks correct, produces no diagnostic anywhere, and quietly removes
a check the author believed they had written.

## Expected behavior

An annotation the skill tells the agent to write is either applied by the toolchain
or reported as wrong. Where a tool defines the exact comment form it parses, the
skill states that form, because form is the difference between an annotation and a
comment that resembles one.

## Actual behavior

The inert form is accepted everywhere in silence: the compiler emits no unknown-tag
diagnostic, no type is imposed, `eslint-plugin-jsdoc` never sees a block to check
(its `jsdoc/no-bad-blocks` covers the single-star form only, and is off unless the
project enables it — the calibration stack for this skill does not), and the
skill's own convention checker is form-blind by construction, since it masks comment
text before any rule runs. Nothing in the stack distinguishes "annotated" from
"annotation silently dropped".

## Minimal reproduction

Re-executed here on TypeScript 6.0.3 under Node 26; three independent limbs.

1. Line-comment form, `checkJs` on:

   ```js
   // @ts-check
   // @typedef {{ id: string, name: string }} User
   // @type {User}
   const u = { id: 1 };
   ```

   `tsc --noEmit --strict --allowJs --checkJs` reports nothing about `id: 1`. The
   same two tags inside a `/** */` block report `TS2322: Type 'number' is not
   assignable to type 'string'`. The check the author wrote never ran.
2. Single-star block form (`/* @typedef ... */`, `/* @type {User} */`) over the same
   declaration: exit code 0, no diagnostic at all.
3. Declaration emit: with `--declaration`, a `/** ... */` description above an
   exported symbol is carried into the generated `.d.ts`; a `//` description above
   the identical export is dropped from it.

The trap that makes the mistake easy: comment form is decided per directive, not by
taste. `// @ts-expect-error` in a line comment does work (verified in the same run),
so an author generalizing from directives that tolerate `//` gets no warning when
JSDoc does not.

## Universality check

The claim is a property of TypeScript's own comment parsing, not of any project,
framework, or lint configuration: JSDoc is read from `/**` blocks only, in every
version of the compiler and in the language service, and the emit behaviour follows
the same rule. It holds identically for `.ts`, `.mts`, `.cts` and JSDoc-typed `.js`,
and for every JSDoc tag, not only `@typedef`. Nothing in the reproduction depends on
the consuming project's stack — the three limbs run against a bare `tsc` invocation.

## Suggested fix (delta-sized)

One rule bullet in `references/lint-clean.md` §"JSDoc on the public surface" naming
the parsed form, the two inert forms, and the verify-by-effect habit; one pitfall in
`knowledge/pitfalls.md` carrying the failure mode and the re-executed reproduction,
with the knowledge index routed to it. No pre-existing rule is altered.

Deliberately out of scope: teaching the bundled convention checker to flag a JSDoc
tag in a `//` comment. It is lexically detectable, but the checker's masker discards
comment delimiters before any rule sees the text, so the rule would require reworking
that masker — a change to an analyzer under mutation scope, disproportionate to a
prose gap and best raised on its own evidence.

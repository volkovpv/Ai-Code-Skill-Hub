# A completeness check may be built from the code it checks, and the skill never said not to

## Context (input)

A field report from a consuming project, verdict class C3 (universal skill
gap), carrying one deterministic, project-independent minimal reproduction.
The reporting project's own reviewer stopped short of transferring it for
five consecutive passes, for a routing reason rather than an evidentiary
one: the principle it names — *derive the case set from the specification,
never from the artifact under check* — was stated in this library only by a
skill whose own declared scope is unit and integration tests, and the
artifact that failed was not a test. The operator's routing decision placed
it in the language standards, next to the rule it widens, because the
failing artifact was production code.

The rule this skill already carried covers a closed set whose ground truth
is a value in the same program (an enumeration, a literal union, the keys
of a declared mapping): key the mapping by it and make the completeness
check explicit and testable. That is the easy half, and it is correct.

## Expected behavior

The same discipline, with the source changed, for a set owned by something
other than this program — a database schema's foreign keys, another
service's enumeration, a protocol's message types, the files in a
directory. The case list is obtained from that owner (introspection,
parsing the specification, walking the directory) and diffed against what
the code handles; a member present in the owner and absent from the handler
is reported by name.

## Actual behavior

The skill was silent on the externally-owned case, and silence here reads
as "the in-program recipe is the whole rule". Nothing told an author that a
registry, guard, allowlist or coverage table built by reading off the cases
the code already implements is self-referential, or that the rule reaches a
verification artifact living in production code rather than in a test
directory.

## Minimal reproduction

Project-independent, and independent of language and stack. A function
`handle(case)` must correctly process every member of an externally defined
set `S` — a schema's foreign-key list, another system's enumeration, a
protocol's message types; anything whose ground truth is owned by something
other than the handler. Build the handler's own completeness check (a
registry, an assertion list, a coverage table) by reading off the cases the
handler already implements, rather than by enumerating `S` itself. Any
member of `S` the handler does not yet implement is then invisible to the
handler and to its own check at once, so the check reports full coverage of
a set it never read. A mutation battery does not surface it either: the
mutants come from the same code the case list was read off, so a member `S`
holds and the code never mentions cannot be mutated into view.

In the reported occurrence the artifact was a foreign-key edge registry
driving a delete order; three consecutive gatekeeper rounds returned a
critical failure on the same underlying shape before it was named, and the
accepted fix was exactly the introspect-and-diff form above.

## Universality check

No project threshold, identifier, path or stack name is involved. The
failure mode is a general software-correctness principle and recurs
identically in any language on any stack; the reported instance is one of
several interchangeable examples the report itself gives (a schema's
foreign keys, an API's enumeration values, a protocol's message types).

## Suggested fix

A delta beside the existing in-program completeness bullet: state the
externally-owned half, the introspect-and-diff form, the reason a mutation
battery does not cover for it, and that the rule reaches any verification
artifact rather than only a test file.

# The duplication guidance names the after-the-fact check and never the before-the-fact search

## Context (input)

An operator-triggered SFL transfer (2026-08-19; not routed through the ordinary
`WF-STATE-013` pipeline — the occasion was a direct operator audit of a
consuming project's build, argued and classified as C3-universal in the
transfer instruction itself, with reproducible measured evidence attached).
`OBS-20260818-001` (Hub PR #24, merged 2026-08-18) already added the
*negative* half of this skill's duplication story: the four cited
SonarJS/ESLint rules are same-file, textual-identity checks, so a fully
green lint run is not evidence that a repeated implementation is absent.
That fix is correct and stays untouched by this one. What it left in place
is the other half of the same gap: nothing in `## Workflow` or `## Rules`
ever tells an author to search the tree, by shape, **before** writing a new
implementation. The skill teaches how to recognize a duplicate after it
already exists; it never teaches how to avoid creating one.

Measured on one live TypeScript service tree (293 files of at least 12 code
lines, comments and blank lines stripped, every identifier and string
literal rewritten to one token, then hashed — a rename-tolerant structural
fingerprint): a prior de-duplication task had already extracted three
shared pieces of logic into a common module, and still left the scaffold
standing around them in ten independently maintained configuration
modules — a shape interface, an error subclass, a resolver, a registration
factory, and an exported type, differing in exactly four values each. Two
of those ten were token-identical after renaming even after that
extraction (one pair 39/39 code lines, one hash; another 35/35). Five
files implementing the same kind of access guard (13 code lines each)
differed in nothing but the guard's class name. Four wiring modules (12
lines each) and three data-access repositories (20 lines each) each formed
a single-hash cluster, differing in 2–4 values. The same tree already held
the correct collapsed shape throughout, one directory away: two shared
utilities (used by 4 and 5 call sites respectively) where each caller kept
only the data that was actually its own — the authors of the ten copies
had a worked example in the same plane and did not look.

## Expected behavior

A skill whose stated purpose includes low duplication would tell an author
*when* to look for an existing home — before the first line, by what the
logic is built out of, never by the name about to be given to the new
symbol — and give a decision order for what to do once something is found
(extend it, call it, or, past a repetition threshold, factor a
parameterized home) before ever reaching for a new file.

## Actual behavior

`references/lint-clean.md`'s duplication bullet, even after `OBS-20260818-001`,
only states what a linter catches after code exists; `SKILL.md`'s
`## Workflow` opens directly at "Type strictly, name explicitly" with no
step for searching first, and no bullet in `## Rules` states a decision
order for extend-vs-call-vs-factory-vs-new-file. Nothing in the skill names
a search strategy, so an author following it exactly writes new code the
moment a requirement arrives, with no instruction to look first.

## Minimal reproduction

Deterministic, project-independent (any TypeScript project following this
skill's stack):

1. `pricing/order.ts` exports `computeOrderTotal(items)`, a small reduction
   over a list of `{ price, qty }` records.
2. A new requirement calls for the identical computation from a different
   module, `checkout/summary.ts`. Following this skill's workflow exactly
   as written before this delta gives no instruction to look at
   `pricing/order.ts` first — an author can satisfy every rule in
   `## Rules` (strict types, no `any`, lint-clean) while writing
   `deriveCheckoutTotal` as a fresh, byte-identical-after-renaming copy,
   and the four SonarJS/ESLint rules `OBS-20260818-001` already describes
   stay silent, exactly as that record documents.
3. Control: with the delta below in place, the first workflow step directs
   the same author to search by shape, find `computeOrderTotal`, and
   either import it or extend it — no duplicate is written in the first
   place.

## Universality check

Nothing above depends on this project's rules, its stack version, or its
file layout — only on the general property that a skill's `## Workflow`
is read and followed in order, and that a workflow with no search step
gives no author a reason to look before writing. `SFL-INV-08`'s first limb
is met by several independently occurring, differently-shaped clusters
measured on the reporting project's own tree (ten configuration modules,
five guards, four wiring modules, three repositories — introduced across
unrelated tasks, one of them *after* a dedicated de-duplication task had
already run); its second limb is met by the reproduction above, which
needs no project file to run.

## Suggested fix

Add a first `## Workflow` step ("Survey before you write") and a `## Rules`
bullet stating the decision order (extend → call → factory at the third
occurrence → new file only once the search comes back empty), detailed in
a new `references/duplication-survey.md`, cross-linked from — not
duplicated into — `references/lint-clean.md`'s existing duplication bullet.
